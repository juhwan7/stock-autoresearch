# 10분 슬롯 센서 · 30분 교대 AI Supervisor

## 목적

GitHub Actions의 10분 센서는 OpenAI API를 직접 호출하지 않는다.

대신 10분마다 AI 없는 객관적 관측을 canonical 슬롯에 저장하고, :00과 :30의 두 ChatGPT Supervisor가 직전 30분의 정해진 슬롯 3개를 이어받아 판단한다.

10분 슬롯 관측·저장 → :00은 :40/:50/:00 3개 슬롯 → :30은 :10/:20/:30 3개 슬롯 → 상대 피드백 검토 → 조사/개선/검증 → 다음 Supervisor 인수인계

이 구조의 목적은 API Key 없이도 10분 해상도의 상태 기록을 유지하고, 단일 snapshot이 아니라 30분 시계열 변화로 판단하게 하며, 스케줄 지연·누락을 숨기지 않는 것이다.

## 10분 GitHub 관측이 하는 일

.github/workflows/연속연구와진화.yml은 `*/10` schedule과 수동 복구 실행으로 다음을 수행한다.

- Toss snapshot을 사용할 수 있으면 가져온다.\n- 네이버 금융의 공개 지수 보조값과 Google News 다중 주제 RSS에서 시장·뉴스 단서를 수집한다.\n- 반도체·AI, 로봇·전력·방산, 바이오·2차전지·자동차, 매크로, 정책·공급망 등 :00/:30 심층 리서치용 handoff query를 함께 남긴다.\n- Health Watchdog을 실행한다.
- Python compile, pytest, git diff --check 결과를 기록한다.
- 직전 GitHub Actions 결과를 확인한다.
- 최근 커밋에서 바뀐 파일을 기록한다.
- 미처리 사용자 피드백 개수를 기록한다.
- 관측 결과를 data/supervisor/queue/YYYY-MM-DD.jsonl에 추가한다.
- 최근 120개 관측을 data/supervisor/recent.json에 유지한다.

이 단계에서는 OpenAI API를 호출하지 않고 새로운 코드를 AI가 생성하지 않는다. 대신 이미 정의된 안전한 자동복구 플레이북은 즉시 실행한다.

- Google News 결과가 비면 검색 필터를 완화하고 broad fallback을 재시도한다.
- 네이버 공개 지수 파서가 깨지면 신형 JSON endpoint와 legacy HTML fallback을 순서대로 시도한다.
- Market runtime이 없거나 오래되면 실제 입력만 읽는 no-AI sensor 모드로 runtime을 재생성한다.
- Risk/Macro runtime이 없으면 no-AI sensor 모드로 일정·Risk 상태를 재생성하며, 실제 매크로 공급자가 없으면 unavailable로 명확히 남긴다.
- Regression Guard 상태가 없으면 10분 루프에서 다시 실행한다.
- 복구 후 Health Watchdog을 다시 실행해 해결 여부를 판정한다.

자동복구로 해결되지 않고 반복되는 문제는 recent.json에 지속 신호로 남아 :00/:30 ChatGPT Supervisor의 코드 수정 우선순위가 된다. 센서의 뉴스 제목은 발견용이며 중요한 사실 확정은 A/B Supervisor가 원 기사와 1차 자료를 다시 확인한다.

## 정해진 3개 슬롯 처리

Supervisor는 단순히 "최근 3개 관측"을 읽지 않는다. 역할과 기준시각에 따라 다음 슬롯만 사용한다.

- B(:30): `:10 → :20 → :30`
- A(:00): 직전 `:40 → :50 → :00`

각 관측에는 `observed_at`과 별도로 `slot_at`, `sensor_interval_minutes=10`, `slot_delay_seconds`를 남긴다. GitHub Actions가 몇 분 늦어도 같은 10분 슬롯 안이면 같은 구간으로 묶는다.

같은 슬롯에 여러 실행이 생기면 validation과 성공 step 수가 더 좋은 관측을 canonical로 선택한다. 같은 슬롯 관측을 2~3개로 세어 Supervisor 입력을 부풀리지 않는다.

예상 슬롯이 없으면 이전 오래된 관측을 몰래 끌어와 3개로 채우지 않는다. 대신 결과에 다음을 남긴다.

- `expected_observation_count=3`
- `received_observation_count`
- `observation_ids`
- `observation_slots`
- `missing_observation_slots`
- `observation_window_start/end`
- `observation_completeness_ratio`

3/3이 아니면 판단 자체를 금지하지는 않지만 canonical 결과는 `verification_pending`으로 유지하고, 누락으로 인해 확신도가 낮다는 사실을 숨기지 않는다.

센서가 :00 또는 :30 슬롯을 기록할 때는 `data/supervisor/windows/YYYY-MM-DD/`와 `latest-A/B.json`에 해당 30분 window manifest를 남긴다. 적용 스크립트도 동일한 규칙으로 window를 다시 계산해 AI 결과를 검증한다.

`last_processed_observation_id` 하나만으로 전체 연속성을 판단하지 않는다. state에는 최근 처리 ID, 마지막 처리 슬롯, A/B별 최근 window를 함께 남긴다. 포인터는 실제 queue에 존재하고 3슬롯 window가 완전한 경우에만 마지막 처리 observation으로 전진한다.

## 사용자 피드백

GitHub Issue #1의 사용자 댓글은 기존 피드백 수집 workflow가 data/feedback/사용자_피드백.jsonl에 저장한다.

1시간 감독자는 새 사용자 피드백을 일반 자동 개선보다 우선해서 읽는다.

처리한 피드백의 마지막 comment id는 data/supervisor/state.json의 last_processed_feedback_comment_id에 기록한다.

## 감독 결과

배치 처리 결과는 data/supervisor/latest-report.json에 저장한다.

주요 필드는 batch_id, observation_ids, observation_slots, observation_window_start/end, expected/received_observation_count, feedback_received/resolved/disagreed/deferred, supervisor_disagreements, status, summary, actions, changed_paths, next_checks, notify다.

status는 no_change, changed, attention, failed 중 하나를 사용한다.

시장·코드 변화가 없어도 :00/:30 Supervisor 사이클 결과는 `notify=true`로 canonical 경로에 기록한다.

Supervisor AI result 파일 push가 canonical 적용 workflow를 발동하고, 적용 후 Telegram 경로가 결과를 전달한다. 10분 센서는 Supervisor 알림을 보내지 않는다.

## 검증 방식

AI가 변경을 적용한 직후에는 validation=pending_next_observation으로 기록한다.

다음 10분 슬롯 관측에서 compile, pytest, diff 검사 결과를 확인한다.

검증 실패가 지속되면 다음 A/B window에서 우선 처리한다.

## OpenAI API Key

이 운영 방식에는 GitHub Repository Secret의 OPENAI_API_KEY가 필요하지 않다.

OPENAI_API_KEY는 사용자가 로컬 또는 별도 실행환경에서 기존 live CLI 엔진을 직접 실행하고 싶을 때만 선택적으로 사용할 수 있다.


## 질문·가설·개선은 :00/:30 두뇌가 담당

10분 센서는 질문을 만들지 않고 `question_queue.json`도 갱신하지 않는다. 신규 공시·뉴스·거래대금·Health·Regression 등 확인 가능한 사실과 원시 상태만 저장한다.

:00과 :30 Supervisor는 같은 연속 기억을 이어받는 두뇌다. 각 사이클에서 최근 원시 관측과 기존 미해결 질문·가설·문제 상태를 읽고 다음 순환을 수행한다.

1. 원시 관측에서 중요한 변화와 이상을 찾는다.
2. 스스로 질문과 반증 질문을 만든다.
3. 1차 자료와 실제 데이터로 답을 검증한다.
4. 프로젝트 부족점이나 버그가 원인이면 안전한 최소 수정과 테스트를 수행한다.
5. 연구 품질을 높이는 새 기능이 필요하면 근거·위험·검증 계획을 세우고 안전한 범위에서 구현한다.
6. 해결 결과에서 다시 새로운 질문을 만들고 다음 Supervisor에 넘긴다.
7. resolved/normal/verification_pending/blocked 상태를 기억해 같은 문제를 불필요하게 처음부터 반복하지 않는다.

즉 순환은 `10분 사실 수집 → :00/:30 질문 생성 → 조사 → 수정/기능 추가 → 테스트 → 새 질문 → 다음 두뇌 인수인계`다.

기존 `question_queue.json`은 10분 센서 출력물이 아니라 Supervisor의 장기 연구 메모로만 사용한다. 질문 수를 성과로 보지 않으며, 실제로 연구 가치가 있는 질문만 보존한다.

## 질문 품질 사후학습

A/B Supervisor가 질문을 조사한 뒤에는 질문 자체도 평가한다. 방향성 예측 적중률만으로 좋은 질문을 정의하지 않는다.

각 처리 질문에 다음 결과를 남긴다.

- question_id / kind
- status: answered / partially_answered / unresolved
- evidence_quality: 0~1, 1차 자료와 독립 교차검증 수준
- usefulness: 0~1, 실제 시장 구조 이해·후속 조사에 기여한 정도
- 새로 생긴 후속 질문과 반증 결과

이 결과는 `data/supervisor/question_learning.json`에 누적한다. 질문 종류별 표본이 최소 10개가 되기 전에는 자동 우선순위 학습에 사용하지 않는다.

충분한 표본 뒤에도 학습 보정은 기본 priority에 최대 +1/-1만 적용한다. 따라서 과거에 유용했던 질문 유형은 조금 먼저 조사하고, 반복적으로 근거가 약했던 유형은 조금 뒤로 보내되 현재의 강한 공시·거래대금 신호를 무시하지 않는다.

목표는 질문을 많이 만드는 것이 아니라 시간이 지날수록 **실제로 답할 수 있고, 근거가 좋고, 다음 판단에 도움이 되는 질문을 먼저 만드는 것**이다.


## 가설 → 사후검증 → 질문 개선

A/B Supervisor 연구에서 충분한 근거가 있는 중요한 결론은 검증 가능한 가설로 `data/supervisor/hypotheses.json`에 등록한다.

예: “14:42에 관측된 로봇 관련 종목의 동시 자금 유입이 다음 2개 관측에서도 유지된다.”처럼 확인 시점과 확인 조건이 명확해야 한다. “로봇이 좋아 보인다” 같은 문장은 등록하지 않는다.

10분 센서는 현재 시각이 `verify_after`를 지난 열린 가설을 관측 데이터에 함께 노출한다. A/B Supervisor는 후속 데이터와 1차 자료를 사용해 confirmed / partially_confirmed / falsified / indeterminate로 판정한다.

사후검증은 질문 품질 학습으로 다시 연결한다. 중요한 점은 confirmed만 좋은 결과로 보지 않는 것이다. 질문이 반증 가능한 가설을 만들었고 실제 데이터로 빠르게 틀렸음을 밝혀냈다면 그 질문도 높은 연구 가치가 있다.

따라서 질문 품질은 다음을 함께 본다.

1. 실제 답할 수 있었는가.
2. 1차 자료·독립 교차검증 근거가 좋았는가.
3. 검증 가능한 가설을 만드는 데 기여했는가.
4. 사후 데이터로 확인 또는 반증할 수 있었는가.
5. 새로운 중요한 후속 질문을 만들었는가.

이 평가가 누적되면 다음 10분 슬롯 질문 생성 시 과거에 실제 연구 가치가 높았던 질문 종류를 제한적으로 우선한다.
